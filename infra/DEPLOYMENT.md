# Локальная инфраструктура и Render

Все команды выполняются из корня репозитория, если не указано иное. Документ описывает действия оператора; подготовка файлов не выполняет облачный deploy, миграции или смену webhook.

## Локальная PostgreSQL 18

Основной путь — `scripts/local-postgres.mjs` из README. Пакет закреплен на версии `18.4.0-beta.17`, скачивается в отдельный npm prefix `.local/postgres-runtime` и не меняет корневой lockfile. В него входят настоящие native binaries PostgreSQL; процесс слушает только loopback, использует SCRAM и отдельные dev/test базы.

Помощник запускается обычным пользователем. При неподдерживаемой платформе или отказе бинарника он завершается с ошибкой: автоматической подмены на PGlite/мок нет. Данные могут содержать тестовую историю, поэтому `.local/` не включается в Docker context и Git.

Альтернатива при установленном Docker:

1. Остановить embedded PostgreSQL, если он занимает `55432`.
2. Задать `LOCAL_POSTGRES_PASSWORD` в своей `.env` и `DATABASE_URL`/`TEST_DATABASE_URL` с этим же локальным паролем, пользователем `splint_local`, адресом `127.0.0.1:55432` и базами `splint_dev`/`splint_test`.
3. Выполнить:

```sh
docker compose --env-file .env -f infra/compose.yaml up -d postgres
docker compose --env-file .env -f infra/compose.yaml ps
```

У PostgreSQL 18 volume монтируется в `/var/lib/postgresql`; `PGDATA` находится внутри версии. Старый путь PostgreSQL 17 `/var/lib/postgresql/data` здесь не используется. Named volume сохраняется после обычного `down`; команда `down -v` удаляет данные и не является обычной остановкой.

## Сборка контейнера

```sh
docker build --tag splint-stage-a:local .
```

Dockerfile собирает npm workspaces на Node 24, удаляет devDependencies, копирует только готовый API, frontend, shared package и SQL-миграции. Runtime работает пользователем `node`. Для SVG-атрибуции PNG установлены базовые шрифты; секреты в image не передаются.

По умолчанию image запускается в production и требует PostgreSQL, Telegram и приватный R2. Не пытайтесь «починить» облачный вход включением demo auth или локальным эфемерным хранилищем. Для воспроизводимых выпусков после проверенной сборки закрепляйте digest базового image; текущий тег `node:24-bookworm-slim` выбирает поддерживаемую линию и допускает исправления безопасности.

## Настройки существующего TestSplint

`render.yaml` — справочный Blueprint. Его импорт может создать новый платный сервис. Для уже созданного TestSplint применяйте настройки существующего сервиса; этот файл не должен создавать дубликат или заменять БД.

| Поле | Значение |
| --- | --- |
| Runtime | Docker |
| Root Directory | Корень данного репозитория |
| Dockerfile Path | `./Dockerfile` |
| Docker Build Context | `.` |
| Branch | `main`, когда подготовленный код действительно находится в этой ветке |
| Docker command | Оставить стандартный CMD image: `node apps/api/dist/server.js` |
| Health Check Path | `/health/ready` |
| Auto Deploy | Выключен в шаблоне; включается отдельным решением после проверок |
| Region | Frankfurt — соответствует созданным тестовому сервису и БД; при использовании внутреннего URL БД сервисы должны находиться в одном регионе |

`PORT` задает Render; приложение слушает `0.0.0.0`. Build/start команды для native Node runtime здесь не нужны. Шаблон содержит один Web Service: отдельные workers будущих этапов не создаются.

Секреты задаются в Environment сервиса: `DATABASE_URL`, `BOT_TOKEN`, `WEBHOOK_SECRET`, `SESSION_ENCRYPTION_KEY`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`. Также нужны точный HTTPS `APP_ORIGIN`, `BOT_USERNAME`, `R2_ENDPOINT`, `R2_BUCKET`. Канонические имена предпочтительны; `postgres` и `bot_token` поддерживаются только как совместимые aliases текущих настроек.

`SESSION_ENCRYPTION_KEY` должен быть случайным и содержать минимум 32 символа; `WEBHOOK_SECRET` — отдельное случайное значение. Они не имеют демонстрационных production-defaults. Оставьте `MEDIA_STORAGE=r2` и `ALLOW_DEV_AUTH=false`. `sync: false` запрашивает значения при создании Blueprint; при обновлении существующего сервиса новые секреты добавляются вручную, не из Git.

## Явные операции после проверки целевой среды

Сначала проверить, что адрес базы относится к новому тестовому Splint, а не к старой или боевой системе. Команды ниже являются инструкцией для уполномоченного оператора; в рамках подготовки репозитория они не выполняются против Render.

Из shell/job с готовым образом и разрешенными переменными окружения:

```sh
node apps/api/dist/cli.js migrate
node apps/api/dist/cli.js seed
```

`tsx` отсутствует в production image, поэтому используются скомпилированные CLI. На платном тарифе явный migrate можно перенести в проверенный `preDeployCommand`; по умолчанию Blueprint его не выполняет. Seed не является шагом каждого deploy.

Для самого первого развертывания пустой БД миграцию нужно выполнить **до** readiness: через отдельно разрешенный pre-deploy command либо одноразовый job с тем же образом и окружением. Ожидать успешного `/health/ready` до появления таблицы миграций нельзя. После успешной миграции приложение может стать готовым с пустым каталогом; seed выполняется отдельным действием, и только после него проверяется пользовательский путь.

Сначала успешные миграция, seed в нужном storage и readiness, затем ограниченный пользовательский тест. Политика rollback — откат совместимого кода; не откат БД старым дампом с потерей новых данных. Схема меняется совместимыми миграциями, с резервной копией и отдельной проверкой восстановления.

Webhook `/integrations/telegram/test/updates` регистрируется оператором отдельно с `WEBHOOK_SECRET`, после проверки принадлежности тестового бота и текущего webhook. Приложение не вызывает `setWebhook` автоматически. Не используйте `drop_pending_updates` при обычном обновлении. Настройки кнопки Mini App и домена также проверяются отдельно.

## Служебные операции Stage A

В доверенной операторской сессии с переменными целевой среды доступны:

```sh
node apps/api/dist/cli.js support:list
node apps/api/dist/cli.js inbox:list
STAFF_ACTOR='operator-name' node apps/api/dist/cli.js support:resolve 'TICKET_ID' 'Причина и выполненные действия'
STAFF_ACTOR='operator-name' node apps/api/dist/cli.js catalog:unpublish 'WORK_ID' 'Причина снятия с каталога'
STAFF_ACTOR='operator-name' node apps/api/dist/cli.js catalog:restrict 'WORK_ID' 'Причина ограничения контента'
```

`TICKET_ID` и `WORK_ID` заменяются проверенными идентификаторами. `STAFF_ACTOR` — запись ответственного в аудит, не самостоятельный механизм авторизации: запуск CLI разрешается доступом к операторской среде и учетной записи БД. Вывод обращений может содержать личный текст и не переносится в публичные логи. Закрытие обращения на удаление не выполняет автоматического удаления данных: сначала оператор выполняет согласованный процесс и фиксирует фактический результат.

## Обязательная проверка перед показом версии

- В контейнере стартует API, раздается готовый frontend и успешно отвечает readiness после миграции.
- Из Telegram проходит подписанный вход; вне production работает только явно включенный demo mode.
- Две вкладки/устройства сохраняют корректный прогресс; старое прохождение не портит перезапущенное.
- Нет открытых исходников/канонических файлов R2 и утечки секретов в логах или bundle.
- Закрытие/открытие приложения сохраняет подтвержденный прогресс; completion появляется в коллекции один раз.
- Ошибки бота не отменяют сохраненный результат; поддержку действительно читает назначенный оператор.

Проверки Docker, cloud readiness, реального Telegram-входа, R2 и backup необходимо отмечать по фактическому выполнению. Локальный тест с PostgreSQL не заменяет их.
